# Plano Especifico de Refatoracao do Data Lake da Fase 1

**Status:** Aprovado para implementacao
**Escopo:** substituir o lake legado baseado em `master_dataset.parquet` por artefatos Parquet separados por granularidade.
**Dependencia:** checkpoint `d8ea5a3` (`fix(phase1): enforce temporal and granularity contracts`)

## 1. Decisoes de arquitetura

A refatoracao nao mantera `master_dataset.parquet`, nao produzira exportacao de compatibilidade e nao tera requisito de migracao retrocompativel. O artefato legado e seus metadados serao removidos pela limpeza seletiva e deixarao de ser gerados pelo pipeline.

A saida do estagio `lake` sera composta por quatro arquivos Parquet independentes em `data/lake/`:

- `student_responses.parquet`
- `evaluator_team_cuts.parquet`
- `git_team_cuts.parquet`
- `transcript_sessions.parquet`

Cada arquivo tera seu proprio sidecar `.metadata.json`, contendo somente o checksum efetivo das entradas, as opcoes relevantes e `status: success`, conforme o contrato geral da Fase 1.

Os dados de avaliadores e Git permanecerao separados. A relacao analitica entre eles sera representada por `git_match_status` no arquivo `evaluator_team_cuts.parquet`, sem copiar metricas Git para as linhas de avaliacao.

## 2. Contratos de granularidade

### 2.1 `student_responses.parquet`

Unidade de observacao: uma resposta individual de formulario.

Chaves e campos obrigatorios:

- `source_type = student_response`
- `Semestre` textual
- `temporal_marker` em `T1`, `T2` ou `T3`
- identificador anonimizado da resposta ou participante, quando fornecido pela fonte anonimizadora

`ID_Equipe` nao sera criado nem inferido para respostas de alunos. As colunas de avaliadores e Git nao pertencem a este contrato.

### 2.2 `evaluator_team_cuts.parquet`

Unidade de observacao: uma equipe em um corte temporal, apos a agregacao de todas as respostas de avaliadores daquela equipe e corte.

Chave analitica:

```text
ID_Equipe + Semestre + temporal_marker
```

Campos obrigatorios:

- `source_type = evaluator_team_cut`
- `ID_Equipe`
- `Semestre` textual
- `temporal_marker`
- respostas ou metricas agregadas do formulario
- `git_match_status`

Valores permitidos para `git_match_status`:

- `matched`: existe atividade Git para a mesma chave
- `no_observed_activity`: nao existe atividade Git observada para a mesma chave

A ausencia de atividade Git nao invalida a avaliacao. A ausencia ou invalidade de `ID_Equipe`, `Semestre` ou `temporal_marker` invalida o artefato e encerra a etapa.

### 2.3 `git_team_cuts.parquet`

Unidade de observacao: atividade Git agregada por equipe, semestre e corte.

Chave analitica:

```text
ID_Equipe + Semestre + temporal_marker
```

Campos obrigatorios:

- `source_type = git_team_cut`
- `ID_Equipe`
- `Semestre` textual
- `temporal_marker`
- `lines_added`
- `lines_deleted`
- `files_changed`
- `num_authors`
- `num_commits`

A ausencia de uma chave Git obrigatoria, uma estatistica numerica invalida ou uma duplicidade ambigua encerra a etapa. Uma equipe sem atividade nao sera fabricada neste arquivo; ela sera representada somente por `no_observed_activity` no dataset de avaliadores quando existir uma avaliacao correspondente.

### 2.4 `transcript_sessions.parquet`

Unidade de observacao: uma sessao ou arquivo de transcricao.

Chave analitica:

```text
session_id + transcript_file
```

Campos obrigatorios:

- `source_type = transcript_session`
- `session_id`
- `transcript_file`
- `Semestre` textual
- `temporal_marker`, quando derivavel de evidencia observavel
- `transcript_text`
- `status`
- `temporal_marker_source`

`ID_Equipe` permanecera ausente quando a fonte nao fornecer vinculo confiavel. Nao sera inferida equipe a partir de texto, nome de sessao ou conteudo da fala.

Quando o corte vier do nome ou caminho do arquivo, `temporal_marker_source` devera registrar `filename` ou `path`. Quando vier do JSON, devera registrar `metadata`. Datas nao observaveis ou fora dos cortes configurados causarao erro explicito.

## 3. Refatoracao do builder

O `03_data_lake_builder.py` sera reorganizado para executar carregamento, validacao e escrita por fonte, evitando a montagem de um DataFrame largo com colunas incompativeis.

### Etapa 3.1: carregamento

- Descobrir fontes recursivamente.
- Rejeitar diretorios obrigatorios ausentes.
- Normalizar `Semestre` para texto na fronteira de cada loader.
- Validar marcadores temporais sem fallback.
- Preservar caminhos relativos de origem.
- Validar tipos numericos de estatisticas Git.

### Etapa 3.2: agregacao

- Agregar avaliadores por `ID_Equipe`, `Semestre` e `temporal_marker`.
- Agregar Git pela mesma chave, sem anexar colunas Git ao dataset de avaliadores.
- Construir o status de correspondencia entre as chaves de avaliacao e Git.
- Preservar alunos e transcricoes em unidades separadas.
- Rejeitar duplicidades que tornem uma chave ambigua.

### Etapa 3.3: escrita

- Escrever os quatro Parquets independentemente.
- Escrever sidecar para cada arquivo somente apos escrita e validacao bem-sucedidas.
- Nao escrever nenhum `master_dataset.parquet`.
- Evitar deixar artefatos parciais quando uma das saidas falhar.
- Usar checksum que inclua todos os arquivos fonte efetivos e opcoes de processamento.

## 4. Limpeza e orquestracao

A limpeza da Fase 1 devera remover permanentemente:

- `data/lake/master_dataset.parquet`
- `data/lake/master_dataset.parquet.metadata.json`
- os quatro Parquets novos e seus sidecars, quando regeneracao for solicitada

A limpeza continuara preservando:

- `data/raw/`
- `data/processed/audio_chunks/`
- `data/processed/transcripts/`
- `data/processed/ner_candidates/`

O estagio `lake` devera produzir somente os quatro artefatos novos e o relatorio JSON de validacao. A ordem fail-fast do orquestrador permanecera inalterada.

## 5. Relatorio de validacao

O estagio devera produzir um relatorio JSON, por exemplo:

```text
data/lake/lake_validation_report.json
```

O relatorio devera conter:

- contagem de linhas por dataset
- schemas e tipos efetivos
- cobertura de `Semestre` e `temporal_marker`
- contagem de chaves duplicadas
- contagem de `matched` e `no_observed_activity`
- chaves de avaliacao sem atividade Git
- status dos testes de PII
- caminhos dos artefatos gerados
- status geral da validacao

O relatorio nao devera conter PII, e-mails, nomes originais, salt ou conteudo de transcricao.

## 6. Testes obrigatorios

Antes da implementacao, os testes deverao ser ajustados para verificar o contrato novo:

- cada loader produz o schema especifico de sua fonte
- `Semestre` e textual em todos os quatro datasets
- marcadores validos sao somente `T1`, `T2` e `T3`
- respostas de alunos nao recebem `ID_Equipe`
- transcricoes nao pareadas nao recebem `ID_Equipe`
- transcricoes preservam `session_id` e `temporal_marker_source`
- avaliadores sao agregados por equipe e corte
- Git e avaliadores permanecem em arquivos distintos
- `git_match_status` distingue correspondencia de ausencia de atividade
- chaves duplicadas causam erro
- chaves ausentes causam erro
- datas fora dos cortes causam erro
- fontes ausentes causam erro
- sidecars sao escritos para cada Parquet somente apos sucesso
- o legado `master_dataset.parquet` nao e criado
- o relatorio de validacao e gerado sem PII

A suite tambem devera cobrir a execucao real com dados temporarios, evitando testes que validem apenas chamadas mockadas.

## 8. Criterios de aceite

A refatoracao sera considerada concluida somente quando todos os itens forem verdadeiros:

1. O pipeline de `cleanup` ate `lake` termina com exit code zero.
2. Os quatro Parquets existem e possuem sidecars `success` validos.
3. `master_dataset.parquet` e seu sidecar nao existem apos a execucao.
4. Nenhum dataset mistura colunas obrigatorias de outra granularidade sem justificativa contratual.
5. Todos os datasets possuem `Semestre`, `source_type` e temporalidade conforme seu contrato.
6. Avaliadores e Git permanecem separados.
7. Avaliadores sem Git correspondente possuem `git_match_status = no_observed_activity`.
8. Transcricoes sem equipe permanecem sem `ID_Equipe` e mantem proveniencia temporal.
9. O relatorio JSON confirma schemas, cardinalidade, temporalidade, PII e sidecars.
10. A suite de testes passa sem regressao.
11. `docs/01.phase1.md`, `docs/00a.general-plan.md` e `README.md` descrevem a arquitetura implementada.
12. Uma busca por referencias a `master_dataset.parquet` encontra somente historico ou texto explicitamente marcado como legado, nao contratos ativos.
