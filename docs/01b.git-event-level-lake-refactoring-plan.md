**Status:** Proposto para implementacao

**Escopo:** preservar a arquitetura particionada do lake, adicionar dados Git em nivel de commit e arquivo, e alinhar toda a documentacao futura aos contratos reais.

## 1. Decisoes confirmadas

Este plano consolida as decisoes da revisao da Fase 1:

- O resultado mais importante neste momento e o Data Lake final da Fase 1.
- A Fase 2 ainda nao foi iniciada; scripts futuros nao devem ser apresentados como implementados.
- O lake nao voltara a produzir `master_dataset.parquet`.
- Os dados permanecerao separados por granularidade e fonte.
- O Git tera um resumo por equipe/corte e artefatos event-level para permitir metricas futuras.
- Deve ser criado `git_files.parquet` para preparar PI e analises por arquivo.
- Deve ser criado `git_commits.parquet` para preservar janelas temporais, autores e commits necessarios para CC e AI.
- Colunas de identificacao dos alunos podem permanecer no lake enquanto seus valores estiverem anonimizados e a regra estiver documentada.
- O texto anonimizado das transcricoes permanece em `transcript_sessions.parquet` para permitir NLP futuro; ele nao deve ser publicado sem auditoria adicional.
- A Fase 2 sera documentada como especificacao futura compativel com os contratos do lake, sem implementar seus scripts nesta refatoracao.
- As conclusoes cientificas devem usar linguagem de associacao observacional, nao afirmar causalidade sem desenho causal apropriado.

## 2. Estado atual e lacunas

Os contratos atuais sao:

- `student_responses.parquet`: respostas individuais de alunos;
- `evaluator_team_cuts.parquet`: avaliacao agregada por equipe, semestre e corte;
- `git_team_cuts.parquet`: Git agregado por equipe, semestre e corte;
- `transcript_sessions.parquet`: sessoes de transcricao por arquivo/sessao/corte.

O resumo Git atual e suficiente para estatisticas descritivas, mas nao preserva todas as evidencias necessarias para a Fase 2:

- timestamp individual de commit;
- hash individual;
- autor local por commit;
- caminho, extensao e status de cada arquivo;
- informacao de renomeacao;
- branch ou ref observada;
- eventos para janelas de 7 dias e 48 horas;
- arquivos nao executaveis anteriores a T1;
- evidencia para calcular PI, CC e AI sem inferencia.

A Fase 2 tambem possui referencias obsoletas a `master_dataset.parquet` e descreve scripts que ainda nao existem. Esta refatoracao deve conciliar essas referencias documentais sem antecipar a implementacao da Fase 2.

Depois da refatoracao, o estagio `lake` produzira seis Parquets independentes:

2. `evaluator_team_cuts.parquet`

## 4. Contratos existentes preservados

### 4.1 `student_responses.parquet`

Unidade: uma resposta individual de formulario.

Obrigatorios:

- `source_type = student_response`;
- `Semestre` textual;
- `temporal_marker` em `T1`, `T2` ou `T3`;
- campos de resposta;
- identificadores anonimizados quando fornecidos pela fonte.

`ID_Equipe` nao pode ser criado ou inferido para alunos. Colunas de identificacao como `Email Address` e `Nome completo` podem permanecer somente se os valores estiverem anonimizados, por exemplo com prefixo `anon_`, e se o relatorio registrar a verificacao estrutural realizada.

### 4.2 `evaluator_team_cuts.parquet`

Unidade: uma equipe em um corte temporal.

Chave:

```text
ID_Equipe + Semestre + temporal_marker
```

Obrigatorios:

- `source_type = evaluator_team_cut`;
- `ID_Equipe`;
- `Semestre` textual;
- `temporal_marker`;
- scores agregados;
- `git_match_status`.

Os nomes longos do Google Forms devem ser convertidos por mapa explicito para nomes analiticos estaveis:

- `engagement_participation`;
- `project_progress`;
- `scope_applicability`;
- `technical_complexity`.

Para cada score, o dataset deve conter:

- `_mean`;
- `_std`, usando desvio padrao amostral `ddof=1`;
- `_median`;
- `_iqr`, calculado como `Q3 - Q1`;
- `_n`, quantidade de respostas validas.

`_n` representa respostas validas observadas, nao necessariamente avaliadores distintos se houver submissoes duplicadas. Com uma resposta, `_std` deve ser `NaN`, nao zero.

Valores de `git_match_status`:

- `matched`: existe atividade Git para a mesma chave;
- `no_observed_activity`: nao existe atividade Git observada para a mesma chave.

Metricas Git nao devem ser copiadas para este dataset.

### 4.3 `git_team_cuts.parquet`

Unidade: atividade Git agregada por equipe, semestre e corte.

Chave:

```text
ID_Equipe + Semestre + temporal_marker
```

Obrigatorios:

- `source_type = git_team_cut`;
- `ID_Equipe`;
- `Semestre` textual;
- `temporal_marker`;
- `lines_added`;
- `lines_deleted`;
- `files_changed`;
- `num_authors`;
- `num_commits`.

Este dataset e um resumo derivado de `git_commits.parquet`. Nao deve ser a unica fonte Git da Fase 2.

### 4.4 `transcript_sessions.parquet`

Unidade: uma sessao ou arquivo de transcricao.

Chave:

```text
session_id + transcript_file
```

Obrigatorios:

- `source_type = transcript_session`;
- `session_id`;
- `transcript_file`;
- `Semestre` textual;
- `temporal_marker` quando derivavel de evidencia observavel;
- `temporal_marker_source`;
- `transcript_text` anonimizado;
- `status`.

`ID_Equipe` deve permanecer ausente quando nao houver vinculo confiavel. O marcador pode vir de `metadata`, `filename` ou `path`, mas a origem deve ser registrada. Datas nao observaveis ou fora do calendario devem causar erro explicito.

## 5. Novo contrato `git_commits.parquet`

### 5.1 Unidade e chave

Uma linha por commit observado no repositorio de uma equipe.

Chave tecnica:

```text
ID_Equipe + Semestre + repository + commit_hash
```

Campos obrigatorios:

- `source_type = git_commit`;
- `ID_Equipe`;
- `Semestre`;
- `repository`;
- `commit_hash`;
- `timestamp` ISO-8601;
- `temporal_marker` quando coberto pelo calendario;
- `ID_Autor_Local` (`Dev_A`, `Dev_B`, etc.);
- `lines_added`;
- `lines_deleted`;
- `files_changed`;
- `branch_or_ref` quando observavel;
- `branch_or_ref_source`.

Regras:

- falhar para equipe, semestre, hash ou timestamp ausente;
- rejeitar chaves duplicadas;
- rejeitar marcadores fora de `T1`, `T2`, `T3`;
- nao inferir `main` ou `master` apenas pelo nome do repositorio;
- nao preservar e-mails, nomes ou aliases de origem;
- registrar indisponibilidade de branch/ref em vez de fabricar valor;
- manter commits fora de um corte somente quando o contrato declarar explicitamente como eventos sem corte aplicavel.

## 6. Novo contrato `git_files.parquet`

### 6.1 Unidade e chave

Uma linha por arquivo alterado em um commit.

Chave tecnica:

```text
ID_Equipe + Semestre + repository + commit_hash + file_path
```

Campos obrigatorios:

- `source_type = git_file`;
- `ID_Equipe`;
- `Semestre`;
- `repository`;
- `commit_hash`;
- `timestamp`;
- `temporal_marker`;
- `ID_Autor_Local`;
- `file_path` relativo ao repositorio;
- `file_extension` normalizada;
- `change_status` (`added`, `modified`, `deleted`, `renamed` ou `copied`);
- `lines_added` quando observavel;
- `lines_deleted` quando observavel;
- `is_binary`;
- `branch_or_ref` quando observavel;
- `branch_or_ref_source`.

Para renomeacoes, preservar `file_path_old` quando fornecido pelo Git. Para binarios, permitir contagens nulas, mas registrar `is_binary = true`. Nunca incluir `.git/`.

O contrato deve preservar todos os arquivos alterados, nao somente extensoes escolhidas. PI filtrara posteriormente extensoes como `.md`, `.txt`, `.drawio` e `.pdf` por regra documentada.

## 7. Refatoracao do parser Git

Refatorar `02_git_parser.py` e a extracao compartilhada para produzir dois modelos intermediarios:

```text
commit_rows -> git_commits.parquet
file_rows   -> git_files.parquet
```

A extracao deve preservar:

- commit hash;
- timestamp;
- autor local anonimizavel;
- repositorio;
- branch/ref observada;
- estatisticas do commit;
- status e caminhos por arquivo;
- renomeacoes;
- semestre e corte temporal.

A leitura do output do Git deve usar delimitadores e formatos seguros para caminhos com espacos, acentos, tabs ou quebras de linha. Nao usar parsing fragil por `split()` em texto ambiguo.

O resumo `git_team_cuts.parquet` devera ser reproduzivel a partir de `git_commits.parquet`, usando a mesma funcao de agregacao do builder.

O checksum deve incluir `repos_list.csv`, opcoes de extracao, configuracao temporal, versao do contrato e identificador do snapshot analisado. Uma regeneracao auditavel nao deve executar `git pull` silenciosamente sem registrar a alteracao do snapshot.

## 8. Compatibilidade com as metricas futuras da Fase 2

### 8.1 Planejamento Inicial (PI)

Depende principalmente de `git_files.parquet`. A futura definicao deve declarar:

- quantidade de arquivos, bytes ou ambos;
- extensoes consideradas nao executaveis;
- tratamento de renomeacoes;
- timestamp de criacao;
- tratamento de arquivos removidos;
- ref Git usada.

Se bytes nao forem observaveis, nao fabricar bytes; usar quantidade de arquivos ou declarar PI indisponivel.

### 8.2 Code Churn (CC)

Depende de `git_commits.parquet` e de um denominador de linhas explicitamente definido. O motor devera:

- aplicar janelas de sete dias pelo calendario configurado;
- somar `lines_added + lines_deleted` na janela;
- usar timestamp ISO-8601;
- falhar quando janela ou denominador nao puderem ser definidos.

### 8.3 Degradacao Tecnica (Delta DT)

Depende de `evaluator_team_cuts.parquet`, usando scores analiticos e estatisticas de avaliadores. A Fase 2 deve declarar qual score ou composicao representa nota tecnica e comparar T1/T3 da mesma equipe e semestre.

### 8.4 Atrito de Integracao (AI)

Depende de `git_commits.parquet` com autor, timestamp e branch/ref. O futuro motor devera filtrar as ultimas 48 horas antes de T3, exigir evidencia de `main`/`master`, contar commits por autor local e calcular Gini somente com dados suficientes.

### 8.5 Indice de Esgotamento (IE)

Pode combinar scores individuais de alunos, respostas temporais e NLP de transcricoes. Sessoes sem equipe devem continuar em nivel de sessao ou corpus e nunca receber equipe por inferencia.

## 10. PII, privacidade e relatorio

O relatorio deve distinguir:

- `pii_status = passed_structural_scan`, quando somente regras deterministicas foram executadas;
- `pii_status = passed`, somente quando a verificacao definida pelo projeto for suficiente para o uso declarado.

A verificacao deve cobrir nomes de colunas, e-mails, identificadores, candidatos anonimizados e texto de transcricao conforme a politica adotada. O relatorio nao pode conter texto de transcricao, e-mails, nomes originais, salt, caminhos absolutos ou conteudo de arquivos.

Como `transcript_sessions.parquet` mantem texto para NLP futuro, o artefato deve ser tratado como privado e nao publicavel sem auditoria semantica adicional.

## 14. Criterios de aceite

A refatoracao sera aceita quando:

1. A execucao real `cleanup -> lake` termina com exit code zero.
2. Os seis Parquets existem e possuem sidecars `status: success`.
3. `git_commits.parquet` possui uma linha por commit e chaves unicas.
4. `git_files.parquet` possui uma linha por arquivo alterado e chaves unicas.
5. `git_team_cuts.parquet` e reproduzivel a partir dos commits.
6. Timestamps, autores locais, caminhos, extensoes e status de arquivo sao preservados sem PII.
7. PI pode ser definido a partir de arquivos sem fabricar bytes ou equipes.
8. CC e AI podem ser definidos a partir de commits, timestamps e autores.
9. Branch/ref ausente nao e substituida por inferencia silenciosa.
10. Os quatro contratos existentes continuam validos.
11. Avaliadores e Git permanecem separados e relacionados apenas por chave/status.
12. O relatorio registra schemas, cardinalidade, temporalidade, PII, sidecars e cobertura event-level.
13. A Fase 2 documentada nao depende de `master_dataset.parquet`.
14. Scripts futuros nao sao apresentados como implementados.
15. A suite completa passa sem regressao.
16. As conclusoes documentais tratam resultados como associacoes observacionais, salvo novo desenho causal.

## 16. Verificacao final obrigatoria da implementacao

Depois de todas as alteracoes de codigo e documentacao, a validacao final deve
ser executada sobre os dados reais do projeto. Testes unitarios ou arquivos
temporarios nao substituem esta etapa.

### 16.1 Execucao ponta a ponta

Executar a pipeline desde a limpeza seletiva ate a geracao do lake usando o
interpretador do ambiente virtual:

```bash
.venv/bin/python run_pipeline.py --from-stage cleanup --to-stage lake
```

A execucao somente sera considerada concluida quando:

- todos os estagios selecionados terminarem com exit code zero;
- o log registrar a conclusao do estagio `lake`;
- nenhuma falha for ocultada por fallback, excecao ignorada ou artefato antigo;
- a limpeza tiver preservado `data/raw/`, `audio_chunks/`, transcricoes brutas
	e candidatos NER conforme o contrato;
- fontes ausentes ou invalidas tiverem causado falha explicita, caso existam.

### 16.2 Inventario dos artefatos

Verificar que `data/lake/` contem exatamente os seis Parquets esperados, seus
seis sidecars e `lake_validation_report.json`:

```text
student_responses.parquet

git_team_cuts.parquet
git_commits.parquet
git_files.parquet
transcript_sessions.parquet
```

Confirmar que nao existem:

- `master_dataset.parquet`;
- `master_dataset.parquet.metadata.json`;
- arquivos temporarios `.tmp`;
- Parquets event-level incompletos;
- sidecars sem artefato correspondente.

### 16.3 Auditoria independente dos schemas

Ler cada Parquet com `pandas` ou `pyarrow`, sem confiar somente no relatorio
produzido pelo proprio builder. Para cada dataset, registrar:

- quantidade de linhas;
- nomes e tipos efetivos das colunas;
- valores distintos de `source_type`;
- cobertura de `Semestre`;
- cobertura de `temporal_marker`;
- quantidade de nulos nas colunas obrigatorias;
- contagem de duplicidades das chaves;

- avaliadores sem colunas de metricas Git;

- media;

### 16.6 Sidecars, checksum e relatorio

Para cada Parquet:

- confirmar `status: success`;
- confirmar a existencia de `input_checksum`;
- confirmar que o checksum cobre todas as fontes efetivas e opcoes do contrato;
- confirmar que o sidecar foi escrito depois da validacao do artefato.

No relatorio, verificar:

- `status: success`;
- contagens de linhas coerentes com os Parquets;
- schemas e tipos coerentes com leitura independente;
- cobertura temporal coerente;

- cobertura de commits, arquivos e branch/ref;
- `pii_status` explicito e semanticamente correto;

### 16.7 PII e privacidade

Executar a verificacao estrutural de PII sem imprimir valores privados. Validar
que identificadores mantidos no dataset de alunos estao anonimizados e que o
texto das transcricoes esta presente somente no artefato privado destinado ao
NLP. O relatorio publico de validacao nao pode conter texto de transcricao.

Se a verificacao for apenas deterministica, registrar
`passed_structural_scan`, e nao declarar ausencia absoluta de PII sem auditoria
semantica adicional.

### 16.8 Decisao de aceite

A implementacao sera aprovada somente se todos os itens abaixo forem verdadeiros:

1. A pipeline real termina com exit code zero.
2. Os seis datasets e sidecars existem e sao legiveis.
3. Os contratos de granularidade e nulabilidade passam na auditoria independente.
4. Os agregados de avaliadores e Git sao reproduziveis a partir das fontes.

6. Nenhuma chave, equipe, corte, branch ou dado de arquivo e fabricado por inferencia silenciosa.
7. O relatorio confirma schemas, cardinalidade, temporalidade, sidecars e PII.
8. O legado `master_dataset.parquet` nao existe.
9. A documentacao da Fase 1 e a especificacao futura da Fase 2 correspondem aos artefatos reais.
10. A suite automatizada passa sem regressao.

Se qualquer item falhar, a Fase 1 permanece pendente, a falha deve ser
registrada e a Fase 2 nao deve ser iniciada com os artefatos nao conformes.
