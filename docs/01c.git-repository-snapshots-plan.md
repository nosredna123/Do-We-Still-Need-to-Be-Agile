# Plano de Implementação: Fase 1.5

**Status:** implementada. Deve ser executada depois da Fase 1 aprovada e antes
da Fase 2 estatística.

**Objetivo:** enriquecer os contratos Git com snapshots estruturais dos
repositórios por equipe, semestre e corte temporal, fornecendo denominadores
observáveis para métricas de Code Churn. A Fase 1.5 não reprocessa formulários,
áudio, transcrições ou anonimização; ela usa apenas repositórios locais já
cacheados, contratos Git anonimizados e calendário versionado.

## Justificativa Metodológica

`cc_total_*` mede volume absoluto de linhas adicionadas e removidas. Sem um
denominador de tamanho, correlações como PI x CC podem capturar diferenças de
escala entre repositórios, equipes maiores, dependências versionadas ou artefatos
gerados, em vez de retrabalho metodológico.

Como os repositórios completos estão disponíveis localmente, medir tamanho por
snapshot é tecnicamente barato. A dificuldade metodológica está em definir qual
tamanho será usado:

- `repo_total_bytes`: tamanho bruto versionado, objetivo, mas mistura código,
  assets, documentos, lockfiles e binários.
- `repo_total_files`: contagem bruta de arquivos versionados, simples, mas
  grosseira.
- `repo_source_files`: arquivos classificados como código-fonte por allowlist e
  filtros versionados.
- `repo_source_loc`: linhas de código-fonte observadas no snapshot; melhor
  denominador para churn rate, desde que a definição de código-fonte seja
  versionada e auditável.

A métrica primária de Code Churn da Fase 2 deve usar `repo_source_loc` quando
ele estiver disponível e válido. Proxies como churn por arquivo alterado ficam
como análises de sensibilidade, não como denominador principal.

## Contratos de Entrada

- `data/raw/repos_cache/`: repositórios Git completos cacheados pela Fase 1.
- `data/raw/repos_list.csv`: mapeamento de `ID_Equipe`, repositório e
  `Semestre`.
- `data/lake/git_commits.parquet`: commits anonimizados com `timestamp`,
  `temporal_marker`, `ID_Equipe`, `Semestre`, `repository` e `commit_hash`.
- `data/lake/git_files.parquet`: arquivos alterados, usado para validações de
  cobertura e sensibilidade.
- `pipeline_config.py`: calendário acadêmico, allowlist de extensões de
  código-fonte e padrões de exclusão.

## Contrato de Saída

`data/lake/git_repository_snapshots.parquet`, com sidecar
`data/lake/git_repository_snapshots.parquet.metadata.json`.

**Granularidade:** uma linha por
`ID_Equipe + Semestre + temporal_marker + repository`.

**Campos mínimos:**

- `ID_Equipe`;
- `Semestre`;
- `temporal_marker`;
- `repository`;
- `snapshot_commit_hash`;
- `snapshot_timestamp` como datetime UTC;
- `snapshot_selection_rule`;
- `repo_total_files`;
- `repo_total_bytes`;
- `repo_source_files`;
- `repo_source_loc`;
- `repo_binary_files`;
- `source_loc_definition_version`;
- `excluded_path_patterns_version`;
- `source_type = git_repository_snapshot`.

## Regra de Seleção de Snapshot

Para cada `ID_Equipe + Semestre + temporal_marker + repository`, selecionar o
último commit observado naquele corte temporal. O snapshot representa o estado
do repositório ao final da atividade observada no corte, não o estado do HEAD
global.

Se não houver commit observado no corte, a linha deve ser marcada como
indisponível com motivo explícito, sem copiar o HEAD e sem inferir continuidade
silenciosa de corte anterior. A decisão de carregar o último snapshot anterior
como estado herdado pode ser adicionada em versão futura, mas deve ser uma regra
versionada separada.

## Medição de Tamanho

O cálculo deve usar APIs Git estruturadas, como `git ls-tree -r -l <commit>`,
sem checkout destrutivo e sem depender da working tree.

**Regras obrigatórias:**

- contar `repo_total_files` para todos os blobs versionados;
- somar `repo_total_bytes` apenas quando o tamanho do blob for observado pelo
  Git;
- calcular `repo_source_files` e `repo_source_loc` somente para arquivos que
  passem pela allowlist de código-fonte e não correspondam a padrões excluídos;
- tratar binários como parte de `repo_binary_files`, sem fabricar LOC;
- falhar se um arquivo textual selecionado para `repo_source_loc` não puder ser
  lido ou decodificado pela regra versionada;
- registrar arquivos ignorados por extensão, caminho excluído ou tipo binário em
  relatório privado de auditoria.

## Definições Versionadas

Adicionar a `pipeline_config.py`:

- `SOURCE_CODE_EXTENSION_ALLOWLIST`: extensões consideradas código-fonte;
- `SOURCE_CODE_EXCLUDED_PATH_PATTERNS`: diretórios e arquivos excluídos, como
  dependências, builds, caches e artefatos gerados;
- `REPOSITORY_SNAPSHOT_CONTRACT_VERSION`;
- `SOURCE_LOC_DEFINITION_VERSION`.

Essas listas devem ser conservadoras e testadas com repositórios temporários.
Qualquer alteração nelas invalida o checksum do contrato de snapshots.
